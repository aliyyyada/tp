# Маршрутные карты: OCR ячеек и связанные таблицы (v3)

Windows 11 x64, Python 3.11 x64. Полностью офлайн во время распознавания: EasyOCR 1.7.2, CRAFT, cyrillic_g2, OpenCV, PyMuPDF. Никаких API или LLM. Обучение новых моделей не выполняется. Основной проект v1 сохранён в main; эта версия — отдельная ветка route-cards-v3.

## Скачать и установить

Готовый комплект: **https://github.com/aliyyyada/tp/archive/refs/heads/route-cards-v3.zip**.

1. Скачайте ZIP ветки и распакуйте целиком. Запустите `ASSEMBLE.cmd`: из `offline-parts` будет собран `routeocr-win11-py311-cpu.zip`, проверен SHA256. На диске желательно иметь 2 ГБ свободного места.
2. Распакуйте полученный ZIP в отдельную папку, например `C:\routeocr`.
3. Если Python 3.11 x64 отсутствует, установите `installers\python-3.11.9-amd64.exe`, включив Python Launcher. Другой установленный Python удалять не нужно.
4. При необходимости установите Microsoft Visual C++ runtime из `installers\vc_redist.x64.exe`.
5. Запустите `install_offline.cmd`. Он создаст `.venv`, поставит все зависимости из `wheels` с `--no-index`, выполнит `pip check` и проверит импорты.

Комплект содержит **CPU-сборку PyTorch**: она работает на ПК с GTX1070 без CUDA. Включены модели EasyOCR. Код не скачивает модели самостоятельно (`download_enabled=False`). Установка именно на Windows здесь не выполнялась: проверялись Windows wheel-зависимости по метаданным, а запуск — на Linux CPU.

### GTX1070 / GPU — отдельная опция

GTX1070 имеет архитектуру Pascal, compute capability 6.1. Для дополнительного GPU-комплекта выбран PyTorch 2.5.1 + CUDA 11.8 и torchvision 0.20.1; CUDA toolkit отдельно для wheels не нужен, но нужен подходящий драйвер NVIDIA.

**CUDA wheels не входят в готовый CPU-архив.** Если нужно ускорение: на Windows ПК с интернетом запустите `tools\prepare_gpu_wheels.cmd` (скачает два больших CUDA wheels), перенесите папку `gpu-wheels` на офлайн-ПК и запустите `tools\install_gpu_offline.cmd`. Общие зависимости уже есть в CPU-комплекте. Затем используйте `--gpu`. Совместимость конкретного драйвера/карты здесь не проверялась; программа проверяет доступность CUDA и архитектуры сборки. Новые CUDA/PyTorch сборки без проверки поддержки Pascal не подставляйте.

## Запуск на Пример.pdf

PDF положите в папку самостоятельно: исходные документы и изображения ячеек не публикуются в репозитории.

Сначала проверьте наложение зон:

```bat
.venv\Scripts\python -m routeocr preview "Пример.pdf" --template templates\primer.json -o preview --dpi 240
```

Затем распознайте:

```bat
.venv\Scripts\python -m routeocr ocr "Пример.pdf" --template templates\primer.json --process-id TP-001 -o result-clahe --dpi 240 --variant clahe --models models
```

`--process-id` — стабильный внутренний ключ процесса. OCR номера документа из шапки сохраняется как **непроверенный кандидат**. Поле шапки `16-05-358` выбрано в шаблоне предварительно: обозначение должен подтвердить технолог. Если номер известен, задайте `--document-number "правильный номер"`: OCR шапки заменён этим подтверждённым значением.

Для сравнения обработки используйте новую выходную папку и `--variant original`, `gray` или `binary`. CLAHE выбран для примера по предварительному сравнению на этом документе. Выходная папка должна быть пустой. Исходное изображение не бинаризуется по умолчанию: бледные рукописные штрихи важно сохранить. Confidence не является точностью, все операции требуют проверки.

## Этапы

1. PyMuPDF растеризует только страницы из шаблона.
2. Поворот на 90/180/270°, при необходимости — перспективное преобразование по четырём точкам `corners` (TL,TR,BR,BL в координатах уже повёрнутой страницы).
3. Шаблон выделяет только нужные поля табличной части и область номера документа. Штампы согласования и материал вне этих зон не распознаются.
4. Каждая ячейка вырезается отдельно, сохраняется PNG, добавляется белое поле. Для оригинала сохраняется цвет, для CLAHE усиливается контраст.
5. CRAFT находит текст внутри ячейки, cyrillic_g2 его распознаёт. Для русских текстовых полей ограничен алфавит декодирования, для числовых — цифры и разделители. У одиночных символов, пропущенных CRAFT, используется дополнительное распознавание области тёмных штрихов; его confidence ограничен 0.5. Такие значения требуют проверки.
6. Результат собирается в сущности и связи по разметке шаблона. Продолжения листов присоединяются к исходной операции явно, а не по догадке OCR.
7. Сохраняются JSON, связанные CSV и Excel, журнал проверки, ячейки и координаты. Ведущие нули и десятичные запятые не преобразуются в числа.

**Это шаблонный способ выделения таблицы.** В комплекте откалиброваны четыре страницы конкретного Пример.pdf. Это не универсальный детектор ГОСТ-форм и не модель автоматического обнаружения операций. Для другого скана нужно проверить `preview` и скорректировать зоны; для новой формы — создать шаблон. Нельзя применять координаты без проверки.

## Сущности: ровно три

`result.json`, CSV и `tables.xlsx` содержат **documents, operations, equipment**.

| Сущность | Содержимое |
|---|---|
| documents | Сам техпроцесс: id, номер документа, источник, флаг проверки |
| operations | Поля операции; `document_id` — ссылка на техпроцесс, `document` — текст обозначений документов операции; `equipment_ids` и `equipment` — связанные записи и названия оборудования |
| equipment | Оборудование/инструмент, инвентарный номер, `operation_id`, `document_id` техпроцесса и список собственных документов `documents` |

В шаблоне `scope=operation` обозначает поле «Документ» операции, `scope=equipment` — документ в колонке оборудования. Документы оборудования не подставляются в поле операции. Несколько документов операции сохраняются строками в `operations.document`. Для конкретной единицы оборудования свой набор хранится в `equipment.documents`. Это не подмена ссылки на техпроцесс: для неё используется отдельный `document_id`. Продолжения операции на следующих листах объединяются по шаблону. Запись equipment относится к конкретной операции; глобальное склеивание одинаковых названий не выполняется.

Внутренняя разметка OCR и связи сохранены отдельно в `ocr_audit.json`, замечания — в `review.json`, изображения и `cells.json` — для проверки. Это технический журнал, а не дополнительные сущности бизнес-модели. На контрольном документе экспорт даёт 1 техпроцесс, 5 операций и 9 записей оборудования; корректность текстов требует проверки.

Если уже есть старый `result.json`, исправить представление можно без повторного OCR:

```bat
.venv\Scripts\python -m routeocr reexport old-result.json --template templates\primer.json -o corrected-tables
```

Для повторного экспорта новой версии входом служит `ocr_audit.json`.

## Шаблон

`templates/primer.json`: страницы, поворот, список полос операций. Все `box=[x1,y1,x2,y2]` нормированы от 0 до 1 относительно повёрнутого/выправленного листа.

- `cells`: имена полей → прямоугольники.
- `resources`: по одному объекту на отдельный ресурс, `kind=equipment/tool/unknown`, `box`, необязательный `inventory_box`.
- `documents`: `box` и `resource_indices` (индексы ресурсов **в этой полосе**, начиная с 1).
- Без `resource_indices` документ связывается с операцией, но связь с оборудованием остаётся неподтверждённой в review.json. Несколько документов в одной зоне нужно разделить на отдельные boxes.
- `continuation_of: "p1/o1"` присоединяет полосу к первой операции страницы 1. Привязка требует проверки технологом; это часть разметки.
- `requires_calibration=true` запрещает обычный запуск до проверки шаблона; для пробного запуска можно явно указать `--accept-template`.

На странице 2 номер/содержание второй полосы сильно выцветшие; они требуют проверки и исключены из контрольной оценки. OCR не подставляет ожидаемый номер операции из примера.

## Фильтр просвечивания и цифры

Опционально добавьте к команде OCR:

```text
--ink-filter --ink-min-contrast 18
```

Фильтр применяется **до** CLAHE. Доступны также `--ink-min-saturation 0..255`, `--ink-max-value 0..255`, `--ink-hue H1 H2` (OpenCV H=0..179). Сохраняются исходные `crops/raw_*.png` и обработанные ячейки. Светлые полезные штрихи также могут исчезнуть; сравнивайте метрики, не включайте жёсткие пороги вслепую.

Подробный разбор MNIST-блокнота, экспорт весов, отдельный NumPy-классификатор цифр, формат данных/объём/ресурсы обучения: **[docs/TRAINING.md](docs/TRAINING.md)**. Веса пользовательской сети не включены: в ipynb их нет. TensorFlow для штатной работы и NumPy-инференса не нужен.

## Точность и проверка

После OCR сформирован `reference.template.json`. Заполните текст каждого поля по изображению, поставьте `verified: true`, сохраните как `reference.json`. Пустая эталонная ячейка допустима (проверяется отсутствие ложного текста).

```bat
.venv\Scripts\python -m routeocr evaluate result-clahe\cells.json reference.json -o metrics.json
```

CER — ошибки по символам; WER — по словам; exact_cell_accuracy — доля полностью совпавших ячеек. Пробелы нормализуются, пунктуация и регистр сохраняются. `--relaxed` дополнительно игнорирует регистр и ё/е. Критерий `--target-exact 0.9` требует **более 90% полностью совпавших ячеек**, результат пишется в `target_met`. Текущая версия не достигает цели. Отчёт показывает долю оценённых ячеек: нельзя выдавать метрики поднабора за точность всего документа. Нет автоматической замены О/0 и исправления значений по ожидаемому эталону.

Предварительная оценка по 73 визуально переписанным ячейкам четырёх страниц (753 символа, 131 слово) лежит в `examples/metrics-*.json`. Это небольшой набор настройки, **не независимый тест и не подтверждённый технологом эталон**. Полный текст эталона и PDF не опубликованы. Новые поля шапки в эту оценку не входят. Сравнивались одни и те же ячейки:

| Вариант | DPI | CER | WER | Полное совпадение ячеек |
|---|---:|---:|---:|---:|
| Tesseract, отдельные ячейки | 240 | 59.63% | 116.03% | 15.07% |
| EasyOCR, исходные настройки | 240 | 32.01% | 79.39% | 38.36% |
| EasyOCR, алфавиты + распознавание числовой ячейки целиком | 300 | 26.69% | 88.55% | 21.92% |
| EasyOCR, алфавиты + резервное чтение одиночных символов | 240 | 22.97% | 77.86% | 39.73% |
| То же + CLAHE | 240 | 21.91% | 67.94% | 39.73% |
| CLAHE + фильтр контраста 18 | 240 | 22.18% | 71.76% | 47.95% |
| CLAHE + фильтр контраста 30 | 240 | 21.91% | 77.10% | 47.95% |

Снижение CER не означает пригодность к работе без проверки. WER и полное совпадение ячеек остаются плохими. Ограничение алфавита может превратить ошибочный символ в допустимый: декодирование записывается в evidence, оригинал сохраняется. Для режимов и норм нужна ручная проверка.

ГОСТ 2.304-81 задаёт начертание, но EasyOCR не обучался специально на этих рукописных картах. Для дальнейшего повышения точности: независимый эталон строк разных авторов/форм, сравнение специализированного HTR и дообучение готового распознавателя на строках чертёжного шрифта. Увеличение GPU-памяти или замена CPU на GPU сами по себе точность не повышают.

## Разработка и воспроизводимость

```sh
python -m unittest discover -v
```

Проверяются связи нескольких ресурсов/документов, продолжения, координаты, метрики и сохранение ведущих нулей/текста в Excel. `requirements-win-cpu.lock` фиксирует все Windows wheel-версии. Внутри офлайн-комплекта `MANIFEST.json` содержит SHA256 файлов, URL моделей и параметры целевой платформы. Дерево models создаётся локально; загрузка моделей отключена.

Для повторной сборки wheelhouse на подключённом Windows ПК:

```bat
py -3.11 -m pip download --no-deps --only-binary=:all: --dest wheels --extra-index-url https://download.pytorch.org/whl/cpu -r requirements-win-cpu.lock
```

Модели: https://github.com/JaidedAI/EasyOCR/releases/download/pre-v1.1.6/craft_mlt_25k.zip и https://github.com/JaidedAI/EasyOCR/releases/download/v1.6.1/cyrillic_g2.zip. Из ZIP извлекаются `.pth` в models. Готовый комплект уже включает их.
